# ハイパーパラメータとプロトコル決定機構の調整アプローチ

`ProtocolManager` におけるプロトコル決定（`check_for_response` および `check_for_initiative`）のハイパーパラメータを決定・調整するための4つのアプローチの比較と具体例です。

## 1. 擬似データによる教師あり学習（ロジスティック回帰）
**概要:** `check_for_response` の `weights_dict`（11次元のシグナルに対する重み）を、人間の直感に基づいた「擬似データ」から機械学習的に逆算するアプローチ。

*   **適用対象:** `check_for_response` の重み行列
*   **方法:**
    1.  「共同注意のときは指差しと視線が強い」といったルールベースのデータ生成スクリプトを作成し、各プロトコルに対する入力シグナル（X）と正解クラス（y）のペアを数百個生成する。
    2.  生成したデータセットに対して、`scikit-learn` のロジスティック回帰（バイアス項なし）を学習させる。
    3.  学習済みのモデルの係数（`clf.coef_`）をそのまま `weights_dict` として採用する。
*   **メリット:** 
    *   手作業で11個の重みを「勘」で調整する沼から抜け出せる。
    *   発達心理学の知見（どのプロトコルにどのシグナルが寄与するか）を、データの分布という形で直接注入できる。
*   **デメリット:** 
    *   静的なルールに基づいて決定されるため、環境の動的な変化やシミュレーションの目的関数（学習の進み具合など）とは連動しない。

## 2. ブラックボックス最適化（Optuna 等の使用）
**概要:** シミュレーション自体を何度も回し、環境全体の目的（幼児の学習効率や自発性の向上など）を最大化するようなハイパーパラメータを自動探索するアプローチ。

*   **適用対象:** `check_for_initiative` の確率パラメータ（`base_request_prob`, `beta_level`, `beta_protocol`, `base_zpd_score` など）や、持続強さ（`persistence`）のスケール。
*   **方法:**
    1.  Optunaなどの最適化ライブラリを導入する。
    2.  各パラメータの探索範囲を定義する（例: `beta_level` は 1.0 〜 10.0）。
    3.  数エピソードのシミュレーションを実行し、「幼児の自発性（`infant_initiative_rate`）と、最終的なレベルスコアの合計」を目的関数として評価し、これを最大化する。
*   **メリット:**
    *   「システム全体として幼児の学習を最もうまく引き出す親の振る舞い」という、動的なインタラクションを考慮した真の最適値が見つかる。
*   **デメリット:**
    *   1回の評価ごとにシミュレーションを回す必要があるため、計算コストと時間がかかる。

## 3. 階層型強化学習（メタエージェント化）
**概要:** `ProtocolManager` を固定の数式や重みではなく、親エージェントの上位ポリシー（強化学習モデル）として学習させるアプローチ。

*   **適用対象:** `check_for_response` と `check_for_initiative` の判断ロジック全体。
*   **方法:**
    1.  `ProtocolManager` をメタコントローラとし、10〜50ステップの大きな時間スケールで「次にどのプロトコルを実行するか（または何もしないか）」というマクロな行動を選択させる。
    2.  「幼児が自発的に新しいタスクを学習したか」「幼児の不快パラメータが下がったか」などを報酬として、PPOやSACなどのアルゴリズムで学習させる。
*   **メリット:**
    *   未知のシグナルや複雑な状況に対して、最も柔軟かつ人間らしい適応行動を獲得できる可能性がある。
*   **デメリット:**
    *   幼児エージェントの学習と親エージェントの学習が同時に進行する（Multi-Agent / Non-stationary 問題）ため、学習が非常に不安定になりやすく、実装・チューニングの難易度が極めて高い。

## 4. 発達段階に応じたカリキュラム（手動スケジュール）
**概要:** パラメータを固定値や最適化で決めるのではなく、エピソードの進行度や幼児の成長（`level_scores` など）に応じて、パラメータを明示的にスケジュール変化させるアプローチ。

*   **適用対象:** `base_request_prob` や `accept_prob` のベース値など。
*   **方法:**
    1.  **初期段階（新生児期想定）:** `base_request_prob` を高く設定し、親主導での関わりを増やす。
    2.  **中期段階:** 幼児の特定のプロトコルレベルのスコアが上がってきたら、`check_for_response` における `accept_prob` を高くし、幼児のシグナルにより敏感に反応するように切り替える。
    3.  **後期段階:** 幼児の自発性（`S_spon`）が十分に高くなったら、親からの介入確率を意図的に大きく下げる（見守りのフェーズ）。
*   **メリット:**
    *   発達心理学の「足場かけ（Scaffolding）」や「フェーディング（支援の引き上げ）」のプロセスを、環境のデザインとして明示的にコントロール・表現できる。
*   **デメリット:**
    *   スケジュールの切り替えタイミングや値の設計を、すべて設計者が手動でチューニングしなければならない。

---

### 結論と推奨される進め方
現状のプロジェクト（デモの早期作成と安定した挙動の確保）に最も適しているのは、**アプローチ1と2のハイブリッド** です。

1.  **静的でルール化しやすい部分（応答の重み）:**
    *   `check_for_response` の11次元の重みは、**アプローチ1（教師あり学習）**で擬似データを作ってサクッと固定値を決めてしまう。
2.  **動的で相互作用によって結果が変わる部分（働きかけのタイミング）:**
    *   `check_for_initiative` の `beta_level` や確率のベース値は、**アプローチ2（ブラックボックス最適化）**を用いて、シミュレーション結果（幼児の成長度）を見ながら決定する。

## 5. 確率計算関数の数式モデル改善案（信号のメリハリ付け）
現状の数式モデルでは、入力シグナルが全体的に弱い（または0の）場合でも、ソフトマックス関数による相対評価で一様分布になり、シグモイド関数の性質上「何もないのに切り替わる」現象が起きてしまいます。これを防ぐための関数定義の改善案です。

### 5.1. 足切り閾値（Threshold）またはダミークラスの導入
*   **課題:** ソフトマックス関数が `response_protocol` の間でのみ計算されるため、「どれにするか」しか決まらず「何もしない」選択肢がない。
*   **解決策:** 
    1.  **足切り:** `strengths` を計算した後、その最大値が一定の閾値（例: `0.3`）を下回る場合は、サイコロを振る前に即座に `False` を返す。
    2.  **ダミークラスの導入による判定の統合と持続強さの活用:**
        ソフトマックスの計算配列に「何もしない（現在のプロトコルを維持する）」というダミークラスを加えます。
        *   **判定プロセスの統一:** 現状は「1. どのプロトコルか（ソフトマックス）」「2. 受け入れるか（シグモイド）」の2段階ですが、ダミークラスを導入すれば「どれにするか（維持を含む）」の **1回のサンプリングに統一** できます。
        *   **持続強さ（persistence）との関連付け:** ダミークラスの「強度（スコア）」として、現在のプロトコルの `persistence` を割り当てます。これにより、「幼児の各プロトコルの要求強度」と「親の現在の行動の持続強さ」が同じ土俵（ソフトマックス関数）で競い合うことになり、数式モデルが非常に洗練され、ロジックもシンプルになります。

### 5.2. ソフトマックスの温度パラメータ ($\tau$) の導入
*   **課題:** プロトコル間の強さの差が小さい時に確率がぼやけてしまう。
*   **解決策:** `strengths` を温度パラメータ $\tau$（0.1 〜 0.5 などの1より小さい値）で割ってから `np.exp` にかける。
    `probs = np.exp(strengths / tau) / np.sum(np.exp(strengths / tau))`
    これにより、少しでもシグナルが強いプロトコルが圧倒的に選ばれやすくなる（Winner-takes-allに近づく）。

### 5.3. シグモイド関数（Acceptance Path）のゲインとバイアスの導入
*   **課題:** `1.0 / (1.0 + np.exp(-(strength - persistence)))` では、両方が0の時に50%の確率で承認してしまう。
*   **解決策:** スケールゲイン $k$ とベースバイアス $b$ を導入する。
    `accept_prob = 1.0 / (1.0 + np.exp(-k * (strength - persistence - b)))`
    *   **$b$ (バイアス):** 例えば `0.5` に設定すると、`strength` が `persistence` より `0.5` 以上高くないと50%の壁を越えなくなり、弱い無意味な信号をシャットアウトできる。
    *   **$k$ (ゲイン):** 例えば `5.0` など大きく設定すると、閾値（バイアス）を超えた瞬間に確率が急激に1に近づくようになり、決定がシャープ（確実）になる。

### 5.4. 親主導の開始判定（check_for_initiative）の課題と改善案
現状の `check_for_initiative` では、最初に `p_request` で「開始するかどうか」をコイントスで決め、その後「レベル選択」と「プロトコル選択」を相対評価（ソフトマックス）で行っています。これには以下の課題があります。

*   **課題1: 状況に適さないプロトコルの強制選択**
    プロトコル選択の段階で、例えば幼児がどこも見ておらず、ターゲットが必要なプロトコル群のスコア（$w_i$）がすべて低い場合でも、相対評価によりどれかが必ず選ばれてしまいます。「状況が整っていないからやっぱりやめる（見守りに戻る）」という選択肢がありません。
*   **課題2: 開始判定と内容決定の分離による機会損失**
    「とりあえず何か始める」と決めてから内容を考えるため、「今、幼児にとって最適な学習のチャンス（ZPDスコアが高く対象を注視している）」であっても、最初の固定確率（`p_request`）を引けなければ見過ごしてしまいます。

**解決策（判定の1段階化への統合）:**
`check_for_response` のダミークラス導入と同様に、「各プロトコルの開始魅力度」と「何もしない（待機）の魅力度」を同じ土俵（1つのソフトマックス）で競わせる1段階判定に変更します。
*   **各プロトコルの魅力度:** `ZPDスコア` $\times$ `注視状態などの環境コンテキスト`。
*   **待機（ダミークラス）の魅力度:** 幼児の自発性（$S_{spon}$）や基本ベース値に依存。
これにより、「良い提案があるときだけ動く」かつ「良い提案がない時は自然と待機が選ばれる」という、より人間らしく柔軟な意思決定モデルになります。
